# 교육·제안·구조화 실행 기준 v19

2026-10-14. 첨부 28개 파일(고유 27종)을 기존 규칙과 대조했다. v2·v3 JSON은
보관본과 동일하므로 51개 의미 구조·24개 조합·20개 차트·92개 규칙을 중복 등록하지 않는다.
[v14 사전](design-contracts-v14.json)은 의미·근거를, [v17](design-standard-v17.md)은
브랜드별 수치를, [v18](structured-slides-v18.md)은 기존 구조 템플릿을 담당한다.
v19는 이를 **추천·미리보기·작성 계획·내용 점검**에 연결한다.

## 1. 실제 반영 범위

| 항목 | 구현 |
|---|---|
| 선택 화면 | 사용 방식·보고 목적에서 질문 추정 → 추천 3개 → 구체 예시 → 필요한 근거 표시 |
| 선택 수 줄이기 | 다른 질문은 접힌 영역, 전체 35개 구조는 요청 시 펼치고 검색 |
| 신규 구조 7개 | 전체도+정의, 질문·정답, 비대칭 요구, 제안 논리, 진단·개선, 단계×필드, 현재·다음·결정 |
| 구체 미리보기 14개 | 신규 7개와 과업 구조·현행/개선·비교표·판단 트리·역할·차트 2종 |
| 정보 모드 | 교육·발표·제안·보고의 모듈과 보존 조건을 별도 기록 |
| 저장 | 기존 확인 화면의 선택값 → `design_profile_v17.json.content_structure`와 `content_plan_v19.json/md` |
| 검수 | 기존 v2/v3 계약을 읽는 `consulting_review.py`; 실제 출력·의미 검토와 분리 |

35개는 선택 가능한 장표 구성 수다. 51개 의미 구조와 같은 분류가 아니며, 35개의
범용 PPT 렌더러를 구현했다는 뜻도 아니다. 14개는 구체적인 HTML 구성 예시이고,
나머지는 기존 슬롯 기반 예시다. PPT 제작은 선택된 기존 실행 경로에서 수행한다.

## 2. 선택과 작성

| 사용 방식 | 독자 질문 | 연결 모듈 | 정보 보존 |
|---|---|---|---|
| 교육·강의 / 교육·배포 | 무엇이며 언제 어떻게 적용하는가 | 범위·전체도 → 정의·요건 → 조건·예외 → 사례 → 질문·정답·이유 | 범위 내 필수 정보를 가시적 본문/함께 배포하는 부록에 배치 |
| 제안 설명 | 왜 이 방안이며 무엇을 납품·확인하는가 | 확인 문제 → 대안·제약 → 과업·산출물 → 이행·완료판정 | 확인 사실, 제안, 계획, 기대효과 구분 |
| 발표 | 어떤 판단이 필요한가 | 핵심 답 → 근거·제한 → 대안 → 결정·행동 | 결론을 바꾸는 조건·예외 유지, 상세 이동 이유 기록 |
| 보고·읽기 | 기준일 현재 무엇이 확인됐는가 | 현재·근거 → 미확인·변경 → 다음 계획 → 결정 요청 | 공시/운영, 검토/승인, 실적/계획 분리 |

교육형과 발표형은 동일 원문 정보 단위에서 각각 작성한다. 짧은 발표 문장을 늘려서
교육형으로 만들지 않는다. 질문과 정답은 교육 자료에 실제로 보이게 둔다.
모듈 순서는 읽기 경로이며 실제 업무 순서를 뜻하지 않는다.

덱 전체의 목차 골격·제목 번호·거버닝 문체·본문 배치는 [v20](content-architecture-v20.md)이 정하고, 이 문서는 장별 구조 선택과 정보 보존 계약을 담당한다.

자동 추천은 사용 목적에 따른 초기 구성 제안이다. 원문을 자동 독해해 의미 적합성을
증명하는 기능이 아니다. 원문의 관계를 확인한 뒤 장별로 구조를 선택하고, 필요하면
다른 구조로 바꾼 이유를 기록한다. 덱 전체에 한 구조를 강제하지 않는다.

## 3. 구조별 보호 항목

| 구조 | 필요한 근거 | 피해야 할 오류 |
|---|---|---|
| 전체도·과업 구조 | 포함 관계, 동일 수준의 개념·과업, 산출물 | 병렬 과업 사이에 순서 화살표 추가 |
| 비대칭 요구사항 | 대상별 요건, 공통 작용 범위·방식, 조건 | A의 6개 요건을 B에 기계적으로 복제 |
| 단계×실행 필드 | 실제 선후관계와 입력·수행·산출 | 발표 순서를 업무 절차로 표시 |
| 판단 트리 | 분기 조건, AND/OR·부정, 결과·후속 행동 | 미확인을 아니오로 처리, 예외 삭제 |
| 제안 논리 | 발주 요구·확인 문제, 제안, 산출물, 완료판정 | 기대효과를 달성 실적이나 근거 없는 절감률로 표시 |
| 진단·개선 | 준거, 공개·내부 증거, 확인 범위 | 공시 미확인만으로 실제 미운영 단정 |
| 진행보고 | 기준일, 현재·다음 기간, 과업 ID, 완료 근거 | 미래 계획을 과거 실적에 포함 |
| 차트 | 원값, 단위·기간·경계·집계·상태, 비율의 분모 | 샘플 값 재사용, 결측 0 치환, 축·총합 왜곡 |

첨부 KSSB 예시는 **구조**의 참고다. 첨부의 조항·날짜가 현행 규정인지 이 작업에서
재확인하지 않았다. 실제 교육자료에 법규 내용을 넣을 때는 그 작업의 원문·버전·조항을
확인한다. 미리보기의 문구와 수치는 모두 가상이며 실제 고객 내용으로 쓰지 않는다.

## 4. 디자인 수치 충돌 처리

현재 사용자·프로젝트 확정값이 우선하고, 그 다음은 선택한 v17 계열·사용 방식이다.
첨부의 `innergen_compact` 16:9·Noto Sans·청록·13.5pt나 PINK 템플릿의 분홍색·12pt를
이너젠 기본·사업소개서·교육강의(블루)·이너캐리 전체에 덮어쓰지 않는다.

v18의 밀집 표 크기와 최소 크기 문구가 충돌하면 **확정된 본문·표 역할의 크기**를
유지한다. 밀도 상한은 분할 검토 신호이며 글꼴 축소 허가가 아니다. 열 폭, 행 높이,
설명 위치, 전체도/상세 분할을 조정한다. HTML 미리보기의 화면상 크기는 PPT 출력
수치 검증을 대체하지 않는다.

원형·면적·화살표·색의 의미는 자료 관계를 따른다. PINK 93장의 3D 차트는 반영하지
않고, 사진 배치 예시는 프레임 관계만 참고한다. 실제 그림은 기존 이미지 수집 단계에서
출처·사용권·캡션을 확인하며, 이 작업은 원본 사진을 새 디자인 자산으로 등록하지 않는다.

## 5. 프로젝트 연결

기존 확인 화면에서 다음 두 필드가 추가로 저장된다.

```json
{"structure_standard_version":"19","structure_goal":"auto"}
```

`structure_goal`은 `auto`, `education`, `proposal`, `requirements`, `procedure`,
`diagnosis`, `progress`, `quantitative`, `overview` 중 하나다. 시각적 사용 방식과
질문은 별도다. 예를 들어 교육·배포에서 요구사항 질문을 고르면 교육형 정보 보존
계약과 비대칭/비교/판단 구조 추천이 함께 적용된다.

```powershell
.venv/Scripts/python.exe .claude/skills/ppt-master/scripts/style_standard.py projects/프로젝트
```

기존 `design_profile_v17` 파일과 함께 `content_plan_v19.json/md`를 만든다.
선택값 또는 v19 카탈로그가 바뀌면 기존 `validate_spec.py`의 스타일 점검에서
오래된 작성 계획을 감지한다. 새 필드가 없는 이전 프로젝트의 검사 계약은 유지한다.
`analysis/source_review_v19.json`이 있으면 같은 검사에서 내용 계약 오류도 함께 확인한다.
기록이 없을 때 내용 검수가 통과한 것으로 표시하지 않는다.

작성자는 `design_spec.md`의 장별 개요에 다음을 기록한다.

| 기록 | 예 |
|---|---|
| 학습/판단 질문 | 조건에 따라 적용 대상이 어떻게 달라지는가 |
| 정보 단위·출처 | 실제 원문 ID·버전·페이지·문단 |
| 관계·구조 | 대상별 상세와 공통층; RCP24 |
| 가시적 배치 | 주장과 조건은 같은 장; 상세·풀이의 장 번호 |
| 미확정·제안 | 원문 없는 담당·기한은 확인 필요; 증빙 제안은 실무 제안 |

이 작업은 새 사용자 승인 단계나 템플릿 자동 설치를 추가하지 않는다. 직접 PPTX 편집
경로에서는 변경 허용 범위 안에서만 의미 점검에 사용하고 원문을 임의 재구성하지 않는다.

## 6. 내용 계약 점검

입력은 [v14 JSON](design-contracts-v14.json)의 `review_schemas.dual_view`(2.0.0) 또는
`review_package`(3.0.0) 형태다. 새 규정 원문을 자동으로 정보 단위로 분해하는 기능은
없다. 작성자가 범위·정보 단위·장별 블록·관계를 먼저 확인한다.

```powershell
.venv/Scripts/python.exe .claude/skills/ppt-master/scripts/consulting_review.py projects/프로젝트/analysis/source_review_v19.json --output projects/프로젝트/analysis/content_review_v19.json
```

자동 점검은 ID·출처 위치, 필수 정보의 선언된 가시적 배치, 보호 구절, 같은 장의 조건,
AND/OR 대응, 연결 근거, 대상 비대칭, 공시/운영 근거, 완료일·증빙, 차트의 일부
수치 계약이다. 실제 PPT/PDF와의 연결은 별도 대조한다. 문자열이 존재한다고 의미가
같다고 단정하지 않는다.

결과의 `PASS_DECLARED_CONTRACT`는 선언된 계약 점검 통과다. 범위 목록이 미검토이거나
필수 정보 분모가 0이면 배치율은 `null`이다. 실제 출력 없이 100% 완성이나 교육자료
배포 승인을 선언하지 않는다. 첨부 QA의 72개 검사와 이번 로컬 검사는 구분한다.

## 7. 출처와 검토 범위

[출처 목록](../../../OUTPUTS/consulting-upgrade-v19/source_manifest.json)에 원본 경로·SHA-256·
보관 경로·중복 여부를 기록했다. PINK는 306장 XML·텍스트와 대표 12장 렌더를 조사했다.
v2 PDF는 10쪽 모아보기, KSSB 예시는 제공 PNG와 PDF 출력을 확인했다. 306장 전수
시각 검수나 원자료 규정의 현행성 검증을 했다고 주장하지 않는다.

화면을 다시 만들려면 다음을 실행한다. 외부 연결이나 서버 없이 열 수 있으며,
선택 파일 저장은 프로젝트 확정·적용을 뜻하지 않는다.

```powershell
.venv/Scripts/python.exe .claude/skills/ppt-master/scripts/consulting_structure.py preview --output OUTPUTS/consulting-upgrade-v19/교육_제안_구조_비교.html
```
